# Lane `check-all`: a real `check_all`, and a bridge that is no longer a no-op

Wave: assembly, 2026-08-08. Ranked item #9 in `docs/mechanics/COVERAGE.md` §6.

## What now runs that did not before

1. **`don_replay::check_all(&don_sim::World)`** — one function, the fifteen channels in
   retail order, the wrapping sum, the value `CheckSums::check_all` actually *returns*, and
   the 65-byte `CheckSumsCommand` wire record. Nothing composed the channels before; there
   was no way to hand a world to anything and get the tuple a retail client would send.
   `cargo run -p don-replay --bin don-replay -- check-all` prints it.

2. **`SimBridge::populate` images `World`'s unit rows into engine layout.** It walks the
   traversal `CheckSums::check_units` `0x009371d0` uses — nine owner slots, unrotated, each
   owner's unit band in `o` order, gated on `SubObjectData::flags & 1` — and writes each row
   into a 344-byte `Unit` image at the PDB's own field offsets. 161 of the 176 bytes the
   checksum visits per unit come from a real column.

   `SimBridge::populate_with_map_checksum` also carries the dynamic `world`
   channel through `map_terrain::World::walk_data`. The authoritative replay
   prefix provides dimensions and seed; unknown generated bytes are counted as
   unsourced rather than omitted or called agreement.

3. **The `units` channel compares byte-for-byte against a real recording.** Driving
   `Playback___2025.02.10_21_26_50__Mon_.rcx` with a populated world (the corpus gate
   `the_bridge_makes_the_units_channel_non_trivial_against_a_recording`): 11,322 compares,
   every one non-trivial, 178 bytes walked per unit per turn, against retail's recorded
   `units_checksum`. It does not match, and it says so.

4. **The scoreboard now reports why it agrees.** Every agreement is labelled `unmodelled`
   (we have no producer) or not, and every compare is labelled with whether *retail itself*
   walked nothing. The measurement that falls out is the point of this lane and is in §5.

5. **The generated `DataWalk` traversal walks sub-objects at their real offsets.** It used
   to walk all 368 of them at `this+0`. Latent while every image was zeroes; wrong the
   moment this lane made an image non-zero.

## 1. `check_all`, and the semantics correction it forced

`docs/mechanics/COVERAGE.md` §1.1 is right and the lane brief (and `README-LLM.md`) are
wrong, so the module implements both halves under names that cannot be confused:

* every channel restarts adler-32 at 1 — sixteen `mov dword [ebp-0x18], 1`, one pre-loop
  plus fifteen channels;
* `edi` accumulates the wrapping sum, and the epilogue stores it **only** to feed
  `SyncLogger::logToMemory` (`0x00936b53`), then returns `[ebp-0x18]` (`0x00936b8c`);
* so `CheckSums::check_all` **returns the fifteenth channel**, `RunTimeEnv`, not the sum.

`CheckAll::returns()` is the return value; `CheckAll::total()` is the sum; a unit test
asserts they differ. The sum reaches the wire from `CommandManager::issue_check_sums`
`0x00940770` as the sixteenth dword at `+61` of a 65-byte record, and `CheckSumsRecord`
encodes/decodes exactly that. The round-trip is tested against `don_net::CheckSums::decode`,
an independently written decoder over the same bytes.

The module also carries `WALKERS`, the fifteen channel walkers as data with the traversal
each one performs, re-read from `re/decomp-all/` for this lane. Three things in it were not
written down anywhere before:

* **`check_units` and `check_guys` iterate 9 owner slots; `check_builds`, `check_walls` and
  `check_cities` iterate 8.** [measured] from the loop bounds: `0xe789dc − 0xe3a390` is
  exactly `9 × 0x6eec`, `0xe71af0 − 0xe3a390` is exactly `8 × 0x6eec`. A unit parked in
  owner slot 9 is processed by `Objects::process_all` (which rotates over ten) and is not
  seen by the units checksum.
* **`check_ammo` gates on `flags & 3`**, not `& 1` like the object channels.
* **`check_deaths` walks a flat array at `Game+0x14c`, stride `0xa4`**, `[0,4)` then, only
  if that dword is non-zero, `[4,0x4b)`. No vtable dispatch, no owner loop.

The owner loop is **not** rotated. `(frame + i) % 10` belongs to `Objects::process_all`;
applying it in the checksum would change the hash every frame for identical state.

## 2. The bridge

`crates/don-replay/src/image.rs` converts a column row to the engine's object using
`don_sim::generated::state::FieldDesc` — offset, size, count, width pool, plane — which is
generated from the shipped PDB's type stream. There is no hand-written field list to drift.

Measured for `UnitData` (`cargo run -p don-replay --bin don-replay -- check-all`):

| quantity | bytes |
|---|---:|
| `sizeof` | 344 |
| written from a column | 218 |
| declared but not materialised (containers, pointers, `String`) | 104 |
| compiler padding / undeclared | 22 |
| **distinct bytes the checksum visits** | **176** |
| … of those, sourced from a column | 161 |
| … of those, nothing produces | 15 |

The walk emits 178 bytes per unit against 176 distinct: two bytes are visited twice, which
is the engine's business, not a bug in ours.

**One substitution, named.** `ObjectData` stores its three coordinates masked
(`value ^ 0x00063637`); `don-sim`'s columns hold the unmasked value, because `World::spawn`
writes a plain `Coord` and `World::pos_x` hands it straight to the movement kernels. The
image applies the mask. This is **not** cosmetic: `SubObject::walk_data` `0x006621d0` walks
`[9,24)`, which contains all three coordinates, so they are hashed on every unit on every
turn and the convention has to be the engine's.

## 3. The walker bug this lane found and fixed

`schema/state-schema.json` records, for each sub-object walk, *where the sub-object lives* —
`['this', 184]` for `Unit`'s `Stack<PathData>`, `['this', 200]` for its `OrderList`,
`['thisload', 68]` for `Object`'s `SimpleArray<int>`. The generator dropped that field and
emitted `Sub { class }`; the walker recursed on the same image at offset 0. All 368
sub-object ops were affected: 131 walked at the wrong offset, 237 walked bytes belonging to
some other object entirely.

It was invisible because every object image in this crate was zeroes, and hashing the wrong
zeroes gives the same answer. Producing a real image is exactly what makes it bite, so it
had to be fixed in the same lane. `WalkOp` now distinguishes:

```
Sub { class, at }        embedded base or member at this+at   — executed
SubPtr { class, at }     pointee of a pointer at this+at      — counted, never executed
SubUnbased { class }     receiver is a global/immediate/stack — counted, never executed
SubUnknown { va }        target class not in the schema       — counted
```

Table-wide (`don-replay walkers`): 20 base-class subs at `+0`, 101 embedded members at a
non-zero offset, 6 behind pointers, 234 unbased, 7 unknown. Refusing to execute the last
three is the difference between a number and a confident wrong number; `WalkOutcome`
carries `ops_sub_unbased` and `is_complete()` accounts for it. `Unit`'s walk reports 17 ops
missed per element and does not pretend otherwise.

**Correction to `crates/don-sim/src/generated/state.rs`.** Its per-field `walked` flag is
computed from each class's *own* `walk_data` and therefore misses everything a base class
walks — it marks `UnitData::flags`, `who`, `o`, `z_internal`, `x_internal`, `y_internal`
unwalked when `SubObject::walk_data` hashes all fifteen bytes of them. This lane stopped
using that flag and takes walked-ness from `walk::WalkedMask`, which executes the real
traversal; the generator should be fixed to propagate base-class ops.

## 4. What the bridge cannot carry

Thirteen of fifteen channels have no producer in `don-sim` at all, and
`check_all::CHANNEL_SOURCE` says so as data, checked against the bridge by a unit test:

> builds, walls, ammo, deaths, groups, guys, leaders, cities, items, goods, rules,
> scenario_data, script_run_time.

`builds` and `walls` are the nearest: `World` already carries the engine's build and wall
*bands* in `ObjectRegistry`, and `crates/don-sim/src/generated/state.rs` already generates
`BuildCols`/`WallCols`/`CityCols` with the same `FieldDesc` tables the unit bridge consumes.
`World` does not hold the rows. Adding `builds` is `PdbColumns for BuildCols` (six lines)
plus a `World` that has somewhere to put a building — the bridge side is done.

Read that as three measured facts:

1. **All 520,397 agreements in the corpus are on channels we have no producer for**, and
   every single one is on a compare where the *engine* also walked nothing. Zero compares
   that agree had our walker touch a byte. Separately, the prefix-derived `world` producer
   walks bytes in all **222,938** comparisons and diverges immediately, so the scoreboard
   now contains a real reconstruction channel without converting failure into agreement.
2. **`walls` is empty in retail for the entire length of all 21 checksummed recordings** —
   `retail_first_nonempty_turn` is `null` in every file. Nobody in this corpus ever built a
   wall. "25,442 turns survived on `walls`" is worth precisely nothing, and now says so.
3. **`ammo` and `deaths` survive exactly until retail's first projectile or corpse.**
   Per file: `survived` = `retail_first_nonempty_turn − 2` in every case (e.g. 3,698 → 3,696;
   2,389 → 2,387). The empty model is right, and then instantly wrong, on the turn the
   recording says so. That is a real deadline, measured from retail, for each channel.
4. **Eleven of fifteen channels are never empty in retail.** `units`, `builds`, `groups`,
   `guys`, `leaders`, `cities`, `goods`, `world`, `rules`, `scenario_data`,
   `script_run_time` are non-`1` from the first checksummed turn (turn 2) of every
   recording. There is no free survival available on them at all.

**The non-trivial comparison.** `don-replay seeded FILE --seed-units N` drives a real
`don_sim::World` — stepped, bridged, walked — against a real recording. On
`Playback___2020.07.25_19_30_12__Sat_.rcx` with 2 owners × 6 units: 171 compares, all
non-trivial, 2,136 bytes walked per compare, 1,032 simulation frames stepped, `units`
divergence at turn 2 and 0 matches. The population is **declared, not derived** — the flag
exists to show the path runs end to end before a producer exists, and a seeded world cannot
match retail. A corpus test asserts it does not.

**What will actually move the number.** Complete one producer. In value order:
the seeded retail `Map::make` body/start placement for `world`, then
`builds`/`cities` (small walked records, 28 and 110 bytes; `World` needs the rows) or
`units` via the in-flight command → order bridge (`crates/don-sim/src/command.rs`). The
moment either spawns from a recorded command, this lane's bridge images it and the
comparison stops being about our absence.

## 7. Open lead: `NextCheckSumCommand` is a second per-turn record nobody has opened

`0x3a`, 6 bytes, `CommandPackage::process_next_check_sum` `0x00945e20`: a `u8 checksum_type`
and a `u32 checksum`, stored into the global table at `0x00cbee90` and logged. It outnumbers
`CheckSumsCommand` 1.63 to 1. Surveyed over the whole corpus for this lane
(`don-replay nextsum --corpus`) [measured]:

```
796,957 records, checksum_type ∈ {0..14} — exactly fifteen values
  type 14: 650,519    type 2: 37,973    type 6: 33,507    type 8: 30,221
  type 5:  22,549     type 3: 12,808    type 13: 6,981    type 12: 993
  type 9:     522     type 11:   518    type 0:     90    type 1:    88
  type 7:      62     type 4:     68    type 10:    58
```

The obvious reading — type is the channel index, value is that channel's checksum — is
**refuted by the corpus**: type 2 would be `walls`, which is constant at `0x00000001` across
all 222,938 packets, yet type-2 records carry thousands of distinct values. Types 4 and 10
carry exactly one distinct value each. Whatever this is, it is a finer-grained per-turn
lockstep record with a fifteen-way tag, it is free, and it is unread. Worth a lane.
