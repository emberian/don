# sim-economy — implementing the derived economy in the simulation core

Lane: **sim-economy**. Input: `docs/derivation/economy.md` (the economy lane's derivation)
and `docs/derivation/rules-constants.json`. Output: the tokenizer, a typed rules block, and
the economy mechanics in the sim core.

All addresses are preferred-base VAs in `ron-bin/riseofnations.exe` (sha256
`30478a44…625079`, image base `0x00400000`). Every claim is marked **[measured]** — I
verified it against this binary on this machine — or **[reported]** — I read it in another
lane's document and did not re-check. Nothing here is verified in the proof-assistant sense
(`docs/CHARTER.md`).

## 2. The tokenizer — `crates/don-rules/src/value.rs`

### 2.1 What the file now does

`value.rs` previously refused to convert values to numbers, on purpose, because the engine's
semantics were unknown. They are known now, so it converts — in exactly two functions, both
ports of retail code, and it still refuses to add a general `to_f32()`.

```rust
pub fn wtoi(s: &str) -> i32;                    // the CRT leaf
pub fn as_scaled(raw: &str, scale: i32) -> i32; // 0x00A1D110, the 40 scaled fields
pub fn as_int(raw: &str) -> i32;                // 0x0057FA60 -> ToInt -> _wtoi, everything else
```

The text-level `RuleValue::parse` stays, with its role narrowed in the module docs: it
describes the *prose* (percent sign, unit word) and **no computed value may depend on it**,
because the engine reads neither. That distinction is now enforced by a test that pins the
two layers disagreeing on `"1.5"` — the engine truncates at the decimal point, `RuleValue`
does not.

### 2.2 The instructions, re-read [measured]

`0x00A1D110`, disassembled here rather than taken from the derivation document:

```asm
00a1d113  mov  edx, [ecx]              ; RString data pointer
00a1d117  jne  0xa1d11f                ; null -> xor eax,eax; ret 4
00a1d11f  test byte [ecx+0xa], 1       ; inline-vs-heap discriminator
00a1d12b  lea  esi, [edx + eax*2]      ;   s = data + 2*offset
00a1d13a  call [0xac54ac]              ; num = _wtoi(s)
00a1d140  push 0x2f
00a1d145  call [0xac5434]              ; sl = wcschr(s, '/')
00a1d150  je   0xa1d16b                ; no slash -> den = 1
00a1d156  call [0xac54ac]              ; den = _wtoi(sl + 1)
00a1d163  jne  0xa1d170                ; den == 0 -> ret 0, BEFORE the multiply
00a1d170  imul ebx, [ebp+8]            ; num * scale, 32-bit, low half
00a1d178  idiv ecx                     ; truncating toward zero
```

Confirms `docs/derivation/economy.md` §2.1 line for line, including the two details that are
easy to get backwards: the zero-denominator early-out happens **before** the multiply, and
`wcschr` searches the **whole string**, so a `/` in trailing prose would open a denominator
in a scaled field. (In shipped data it never does — the eight values with a slash in their
prose are all `_wtoi` fields. A mod moving one into a scaled field would break.)

### 2.3 Test expectations, captured not calculated

Three sources, in descending order of authority:

1. **The whole shipped corpus.** `engine_tokenizer::reproduces_the_whole_shipped_corpus`
   iterates all **832 recovered slots** from `rules-constants.json` and asserts
   `parse(xml_value, field_scale) == stored`. **All 832 pass** [measured]. Those
   expectations are not mine: 828 of the 834 extracted constants (834 counts two fields
   twice, from two binder sites) were read back byte-for-byte out of a *running match's*
   `RULES` object, per `docs/provenance-ledger.md`. So this test is the parser against the
   running game's memory, not against itself.
2. **The 16 retail vectors** captured by the economy lane's oracle (`economy.md` §2.2),
   asserted verbatim.
3. **Structural edges only where no arithmetic is involved** — zero denominator, no leading
   digits, empty string. I deliberately did *not* write expectations like
   `as_scaled("  7 / 2 ", 100) == 350`: that would be me calculating what the binary does,
   which is the rule this project has already paid for breaking once.

### 2.4 What is still open in the tokenizer

- **`_wtoi` on overflow.** The Tier-B harness *substituted* `_wtoi` (it patched IAT slot
  `0x00AC54AC`), so the differential claim never tested MSVC's own leaf. Our `wtoi`
  accumulates with wrapping. Whether the real CRT wraps or clamps at `INT_MAX` is **not
  established**; no shipped value has more than 4 digits. Documented in the function.
- **UTF-16 vs `&str`.** The engine parses wide characters; we take UTF-8. Identical on every
  ASCII input, which is all of the shipped corpus. A mod with non-ASCII digits would diverge.

## 3. The economy mechanics — `crates/don-sim/src/mechanics.rs`

Design follows the damage port's precedent exactly, and for the same reason: **arithmetic is
ported, object-graph guards are inputs.** `EconomyRules` carries the rule constants (each
field documented with its offset, its shipped value, and the VA that reads it);
`ResourceTickInput`, `CommerceCapGates`, `AttritionInput` and `AttritionPredicates` carry
everything the engine gets by walking players, units and the game object. Nothing invents a
predicate it cannot resolve.

`don-sim` still has **no dependencies** — `EconomyRules` mirrors the layout of
`don-rules::Rules` by offset rather than importing it, which keeps the sim core free of the
rules crate exactly as `CombatRules` already does.

### 3.1 The resource tick — `Player::TickResource` `0x006CE450` [measured]

**The tick runs once per frame per player**, which `economy.md` did not establish. The call
chain, each link confirmed by an xref scan of `.text`:

```
FUN_00591EF0   the frame update; increments the frame counter at game+0x550
  -> FUN_006ED2A0    loop over players (flag bit 1)
    -> FUN_006CE280  zeroes the six expense slots, then:
      -> FUN_006CE900   UpdateCommerceCaps
      -> FUN_006CE450   TickResource
```

`FUN_006ED2A0` has exactly one caller (`0x0059224F`) and `FUN_006CE280` exactly two; there is
**no modulo gate anywhere on the chain**. The periodicity is entirely in the accumulator:

```
period = GATHER_RATE * 16 = 7200          ; 0x006CE7B9, shl ecx,4
whole  = income / period                  ; 0x006CE7C5, idiv
acc   += income % period                  ; 0x006CE7DE, stored ^0x3421 at econ+0x18+res*4
while (acc >= period) { acc -= period; whole++ }   ; 0x006CE810
stockpile += whole                        ; 0x006CE855, stored ^0x8221
```

So an income of `I` per frame credits `I/7200` resources per frame — i.e. `I` is sixteenths
of a resource per `GATHER_RATE` frames, and `GATHER_RATE` = 450 frames = 30 s at the engine's
15 fps.

**The 15 fps is now [measured] in the binary**, not just asserted by the `rules.xml` header
(`crates/don-sim/src/lib.rs` says it "has not yet been confirmed against the binary" — it can
be updated). `0x005924BF` increments the frame counter at `game + 0x550`, and `0x005924CF`
immediately does `idiv 15` on it and, on a zero remainder, increments a second counter at
`game + 0x560`. Fifteen frames, one tick of that counter.

The carry loop is ported as a loop, not folded into the division,
because a remainder left over from earlier frames genuinely changes the frame a payout lands
on — there is a test that drives it a frame at a time.

The pipeline, in retail order — which is **not** the order `economy.md` §3.2 gives (§4.1):

| # | step | VA |
|---|---|---|
| 1 | `income = (econ[0x64] ^ 0x872) − (econ[0x7C] ^ 0x26076) + player[0x4B0]` | `0x006CE4C8` |
| 2 | `income < 0` → cache the display value and **abandon the resource** | `0x006CE4E7` |
| 3 | clamp to the commerce cap | `0x006CE512` |
| 4 | interest (gated `res != 3 && FUN_006E1370(0x16)`): `+= (DUTCH_INTEREST × surplus / 100) << 4`, clamped to `(DUTCH_INTEREST_CAP << 4) + cap` | `0x006CE6C2` |
| 5 | **only on that same gated path**: `income = min(income, 16000)` | `0x006CE706` |
| 6 | cache the displayed income at `econ[0x94] ^ 0x90236` | `0x006CE723` |
| 7 | gather-rate bonus `× (100 + FUN_006D66A0) / 100` | `0x006CE72C` |
| 8 | knowledge only, difficulty > 4: `×3/4` (5–6) or `/2` (>6) | `0x006CE755` |
| 9 | `game[0x20] & 2` or `game[0x2A] == 9`: `×3/2` | `0x006CE783` |
| 10 | game speed > 1: `× speed` | `0x006CE79C` |
| 11 | accumulate as above | `0x006CE7AE` |

Every `/100` is the `0x51EB851F` magic (signed truncating); the `×3/4` and `×3/2` are
bias-then-shift, also truncating. All multiplies are 32-bit `imul`/`lea`, so the port wraps.

### 3.2 Commerce caps — `Player::UpdateCommerceCaps` `0x006CE900` [measured]

- The cap is indexed by the player's **age** (`econ[0xF0] ^ 0x63187`), reading
  `RULES[0x400 + age*4]` — shipped `70,100,150,200,260,320,400,500` (`0x006CE940`).
- **Knowledge is hardcoded 999** — `0x006CE92C` stores the literal `0x1166`, and
  `0x1166 ^ 0x1281 = 0x3E7`. The `jmp` immediately after it skips every bonus, so no civ or
  wonder term can move it. It is not in `rules.xml` at all.
- British (`FUN_006E1370(player, 0xB)`) multiplies every resource by
  `(100 + BRITISH_COMMERCE) / 100`; then one mutually-exclusive per-resource branch applies
  `INCA_WEALTH_CAP` (wealth, prop 2, `0x006CE9A9`), `FRENCH_TIMBER_COMMERCE` (timber, prop
  0xA, `0x006CEA04`) or `EGYPTIAN_FOOD_COMMERCE` (food, prop 7, `0x006CEA5C`). Slots 4 and 5
  have **no** per-resource branch.
- Each branch is skipped when its rule is 0 (`test eax,eax; je`), so a zeroed rule never even
  queries the property.

Those three per-resource branches are also the only evidence for the resource ordering, so
the crate names exactly four slots (`RES_FOOD` 0, `RES_TIMBER` 1, `RES_WEALTH` 2,
`RES_KNOWLEDGE` 3) and refuses to name 4 and 5. The wiki's ordering is not evidence.

The additive wonder terms from `0x006CEAA6` on are each gated by their own wonder/tech check
and are **not** derived; `commerce_cap` takes their sum as an input, so passing 0 models "no
wonders" honestly.

### 3.3 The rate ramp — `0x00650AB5` in `FUN_006508C0` [measured]

```
base  = x * UNIT_RATE_BASE / 100                        ; 0x00650AF6
count = (u16) players[0x56FE + (player*0x3776 + type)*2]; 0x00650B17
ramp  = count * JOB_EXTRA_TIME * UNIT_RATE_PROGRESSION  ; 0x00650B27, 0x00650B31
out   = clamp(base + ramp, 0, 3*base)                   ; 0x00650B3D
```

with `JOB_EXTRA_TIME` = `UnitType + 0x2E8`. Implemented as `ramped_rate`, plus
`rate_after_game_option` for the follow-on `v * (200 − FUN_006DA740) / 200` at `0x00650B67`
— note the `/200`, whose `sar edx, 6` is one bit off the `/100` idiom and reads exactly like
it at a glance.

**It is not train time.** `x` comes from `UnitType` vtable `+0x6C`/`+0x70` and this crate has
no `UnitType`; `economy.md` §4.2 flagged the same gap and said not to implement it as train
time. So the function is named for the arithmetic, documents the gap, and is not wired to
anything.

### 3.4 Attrition — timing, which `economy.md` left open [measured]

This is the lane's main new derivation, and it changes the *meaning* of the function.

`FUN_00608FD0` does not return a damage multiplier. It returns an **interval scale** in 8.8,
and its consumer turns that into a **frame period**:

```asm
005e192e  call 0x608fd0                ; scale
005e1937  je   skip                    ; scale == 0 -> no attrition at all
005e1942  mov  eax, [rules+0xd3c]      ; ATTRITION = "48 frames"
005e1948  imul eax, ecx
005e1951  cdq / and edx,0xff / add / sar eax,8   ; trunc(ATTRITION*scale/256)
005e195f  cmovg ecx, eax               ; floor of 1
005e1962  ...  word [ebx+0x9e] = min(existing non-zero, this)
```

and `unit + 0x9E` is consumed at `0x006117C8` as

```asm
006117c8  movzx edx, word [ebx+0x9e]   ; period
006117d2  je    skip                   ; 0 = no attrition
006117d9  movsx ecx, word [ebx+0xa]    ; per-unit phase
006117dd  mov   eax, [game+0x550]      ; frame
006117e9  idiv  ecx
006117eb  test  edx, edx               ; (frame + phase) % period == 0
```

So **attrition fires when `(frame + unit[0x0A]) % period == 0`**, and the whole per-unit
attrition state is recomputed every 32 frames on the same stagger (`0x006115EA`:
`(frame + phase) & 0x8000001F` with the sign fixup, i.e. signed `% 32`, gating the
`call 0x5e11a0` that contains the site above).

That resolves the puzzle `economy.md` §5.2 raised and told us to resolve before implementing
— "`edi / ebx` makes the returned strength *decrease* as the level integer rises, which is
the opposite of the intuitive reading". It is not a strength. A higher attrition level yields
a **shorter period**, i.e. more frequent ticks. The decisive independent witness is the
assassin path at `0x005E15DD`, which stores `ASSASSIN_ATTRITION` — `"8 frames"` in the
shipped XML — into the same word with no scaling at all, and halves it for air units.
`merge_attrition_period` keeps the **minimum** non-zero period, so the fastest source wins.

The interval function itself, re-derived (see §4.3 for where this differs from `economy.md`):

```
level = players[attacker][0x7F0];  if 0 -> 0                    ; 0x00608FED
if RULES.ATTRITION == 0 -> 0                                    ; 0x00608FFE  (master switch)
v = 0x100
if siege_class:  SIEGE_ATTRITION >= 100 -> 0                    ; 0x00609027
                 else v = 25600 / (100 - SIEGE_ATTRITION)       ; 0x0060903D
if HasAbility(0x42): v = v*100 / (100 + MILITIA_ATTRITION)      ; 0x0060907B
else:                v = cvttss2si((f32)v * player[0x7F4] * 1/256f)   ; 0x0060913E
                     if FUN_006DB810(owner,0x2FE) && FUN_0046FA40(unit) -> 0
if type id in {0x3D,0x3E,0x190}: v /= 2                         ; 0x00609096
if domain == 2:                  v /= 2                         ; 0x006090A8
ageDiff = attackerAge - unitOwnerAge
if ageDiff >= 0: level = (level*(100 + ATTRITION_AGED_UP*ageDiff) + 99) / 100   ; ceiling
return v / level                                                ; 0x0060911B
```

The float branch is ported with a `cvttss2si` helper rather than Rust's `as i32`: `as`
saturates and maps NaN to 0, while `cvttss2si` returns `0x80000000` for NaN, infinities and
out-of-range. The multiplier at `player + 0x7F4` is engine-written float we do not control,
so the difference is reachable.

### 3.5 Cost ramping — the derived fragment only

`FUN_00664090` is ~12 KB, skipped by the bulk decompiler, and `economy.md` §4.3 located but
did not reduce it. Two pieces have addresses and are ported; the rest is not:

- `cost_ramp_ceiling(base, ramp_max_pct)` = `base * ramp_max / 100` (`0x006656AA`), where
  `ramp_max` is one of `UNIT_SCHOLAR_RAMP_MAX` 2000 / `UNIT_WORKER_RAMP_MAX` 500 /
  `UNIT_OTHER_CIVILIAN_RAMP_MAX` 200 / `UNIT_MILITARY_RAMP_MAX` 125. **Which class a unit is
  in is not derived**, so the selection is the caller's.
- `clamp_cost_to_ramp_ceiling(cost, ceiling)` (`0x00665452`) — and note that a **zero ceiling
  means no ceiling** (`test esi,esi; je`), which is the opposite of the natural reading and
  is exactly the kind of thing a `min()` would have silently gotten wrong.

The accumulation loop it sits in reads a two-slot cost table at `UnitType + 0x270` with the
resource ids eight bytes below (`0x00665443`), then applies `(100 − MAIZE_RAMPING_BONUS)/100`
under two player-bitmap tests. I did not port that: the multiplier `edi` it scales the cost
by is not derived.

**`SUPPORT` and `PROGRESSION` are not implemented, at all.** The task named them, and
`economy.md` §4.1 sources them **only** to BHG's prose in `ron-data/unitrules.xml` — no
engine site has been tied to either name. Implementing a ramp curve from that prose would be
precisely the folklore the charter forbids, so it is listed in §5 instead.

## 4. Corrections to `docs/derivation/economy.md` [measured]

Every one of these came from disassembling the address the document cites. They are not
criticism of that lane — its structural work is what made this cheap — but they are all
places where transcribing the prose would have shipped a wrong simulation.

### 4.1 The income pipeline order is wrong, and two steps are missing

`economy.md` §3.2 lists the interest term as step 1 and the 16,000 cap as step 2,
unconditional. Retail:

- **The negative-income early-out is missing entirely.** `0x006CE4E7` (`jns`) caches the
  display value and jumps to the loop increment: no accumulation, no stockpile write. A port
  built from the document would credit resources on a deficit.
- **The commerce-cap clamp is missing.** `0x006CE512` clamps the income to
  `econ[0x30 + res*4] ^ 0x1281` *before* the interest term. The document mentions only the
  interest branch's own clamp.
- **The 16,000 ceiling is conditional.** `0x006CE62F` (`cmp ebx,3; je 0x6CE715`) and
  `0x006CE643` (the `FUN_006E1370(0x16)` test) both jump **past** `0x006CE706`. Knowledge —
  and any player without that property — has no ceiling. Ghidra's C agrees with the
  disassembly here; the document does not.

### 4.2 The interest clamp shifts the wrong operand

`economy.md` §3.2 step 1: "clamped to `(econ.commerce_cap[res] + rules.dutch_interest_cap) << 4`".
The machine code at `0x006CE6F6` shifts **only the rule constant**:

```asm
006ce6f0  xor  ecx, 0x1281        ; ecx = commerce_cap
006ce6f6  mov  eax, [rules+0x8ac] ; DUTCH_INTEREST_CAP
006ce6fc  shl  eax, 4
006ce6ff  add  eax, ecx           ; limit = (rule << 4) + cap
```

With the shipped 50 and an age-0 cap of 70 that is 870, not 1920 — a factor-of-2.2
difference on the Dutch economy.

### 4.3 The attrition branches are an if/else, not a sequence

`economy.md` §5.2 presents the militia adjustment as an independent `if` and the float
conversion as "the alternate branch at `0x00609122`". They are the two arms of one `if/else`
on `HasAbility(0x42)` (`0x00609047` → `0x0060905E`, `test eax,eax; je 0x609122`). A unit
either takes the integer militia path or the float path, never both. The float arm also
carries two further predicates (`FUN_006DB810(owner, 0x2FE)` and `FUN_0046FA40(unit)`) that
can return 0 — full immunity — which the document does not mention.

### 4.4 "Income is carried in 1/16-resource units — every contribution is `shl eax, 4`"

Only the **interest** contribution is shifted (`0x006CE6DC`, inside the surplus branch). The
base income at `0x006CE4C8` is not shifted at its site. The 1/16 reading is still the
consistent one — the accumulator period is `GATHER_RATE * 16` — but it rests on the
*producers* of `econ + 0x64` emitting those units, and those producers are not derived. Worth
stating because the commerce cap is compared against the unshifted income at `0x006CE512`,
which is dimensionally odd and unresolved.

### 4.5 Small ones

- The rate-ramp core is at `0x00650AB5`, not `0x006508EB` (which is not an instruction
  boundary — it is inside the 3-byte `mov eax,[ecx+4]` at `0x006508EA`).
- The per-type count is at `players + 0x56FE + (player*0x3776 + type)*2`; §4.2 omits the
  per-player stride.
- The `game[0x2D] == 8` branch at `0x006CE48F` sets every stockpile to `0x104BE ^ 0x8221` =
  **99999** and skips the tick — an infinite-resources mode the document does not mention.
  Not implemented (its gate is a game-config byte we have not derived).

## 5. Not implemented, and why

Listed rather than filled in, per the task and the charter. Each of these has a real gap
behind it, not a shortage of effort.

| thing | why not |
|---|---|
| **Worker → income composition** | `economy.md` §3.2 is explicit that the expression turning worker counts, `CITY_GATHER`, `BASIC_GATHER`, `SCHOLAR_RATE` and the six building-bonus tables into `econ + 0x64` is not derived. `PEASANT_RATE` (2560 = 10.0 in 8.8) and `OIL_RATE` (8960 = 35.0) are in the typed rules block, unused. `resource_tick` takes the gross as an input. |
| **The interest threshold** | Built at `0x006CE666`/`0x006CE684`/`0x006CE69A` from a game-config table and, on one branch, `RULES[+0xA60]`. Supplied whole as an input. |
| **`SUPPORT` / `PROGRESSION` cost ramping** | Sourced only to BHG prose in `unitrules.xml`. No engine site is tied to either name. Not implemented in any form. |
| **The rest of `FUN_00664090`** | ~12 KB, dozens of gated modifiers, decompiler-skipped. Only the ramp ceiling and its clamp are ported. |
| **What `x` is in the rate ramp** | `UnitType` vtable `+0x6C`/`+0x70`. Until it is known, `ramped_rate` is arithmetic, not train time. |

## 7. What would raise the economy above Tier C

In priority order, and none of it is cheap:

1. **A `TickResource` harness.** `0x006CE450` needs a fabricated player array (stride
   `0x6EEC`), an econ block at `+0x6EB8`, the game object at `[0x00C061EC]`, `RULES`, and
   stubs for `FUN_006E33A0`, `FUN_006E1370`, `FUN_006D66A0`. That is the same shape of work
   `crates/oracle/src/damage_env.rs` already did for the damage chain, and it would take the
   whole pipeline to Tier B in one go.
2. **A live read of one player's econ block** across a few frames of a running match. It
   would settle the income units question (§4.4) directly, which no amount of disassembly
   will.
3. **`FUN_006CEEE0`** — the function `FUN_006CE280` calls with the six gross-income slots. It
   is the doorway to the worker→income composition, the single largest hole left in the
   economy.
