# Do replays embed periodic simulation checksums?

Lane: `replay-checksum`. Every claim is marked **[measured]** (I verified it against
`ron-bin/riseofnations.exe`, against the replay corpus on the VM, or against the live
process) or **[reported]** (read somewhere, unchecked). Nothing here is "verified" in the
proof-assistant sense — see `docs/CHARTER.md`.

---

## Headline

**Yes — multiplayer replays carry a complete 15-channel simulation checksum on *every*
turn, for *every* player. Single-player replays carry none, and this is structural, not
incidental.**

In the 2025 multiplayer replay recorded by **exactly our binary's build**
(`Version: 00.2024.06.20`), **22,642 of 22,642 command packages — 100.0000% — contain a
`check_sums` command** [measured]. Across three multiplayer replays: **54,947 checksum
packets, 824,205 individual channel values, all 824,205 adler-32-shaped, 0 exceptions**
[measured]. Across 27,473 turns where both players reported, the two players' 16-tuples
were **byte-identical 27,473 times, 0 divergences** [measured].

The single-player replay `ron-data/replays/today.rcx` contains **0 of 10,532** [measured].
The reason is in the sender's gate (§4): the `check_sums` command is only emitted when the
network-game flag is set.

Two corrections to `docs/derivation/checksum.md` fall out (§3):

- The `CheckSumsCommand` is **`0x41` = 65 bytes, not `0x3d` = 61**. There is a **sixteenth**
  `u32` at `+0x3d` carrying `total`. Confirmed three ways: `push 0x41` at the send site, the
  handler's `return 0x41`, and 54,947 packets in which the 16th word equals the wrapping sum
  of the first 15.
- `check_all` (`FUN_00936560`) is the *display/local* walk. The **packet builder is a
  separate function, `FUN_00940770`** [measured, newly located], which walks the same fifteen
  channels in the same order and appends the 65-byte command.

**This is the per-frame oracle the project wanted, and it arrives from a file format.** A
`.rcx` from a multiplayer game is a command stream plus a ground-truth 15-way state hash at
every single turn. Divergence between our Rust sim and retail localises to an exact turn and
an exact channel with no instrumentation of the running game at all.

## 1. What a `.rcx` command stream actually is

`docs/replay-format.md` had the container (single gzip stream from offset 0) but not the
framing. The framing is now recovered [measured].

After the header/initial-state blob, the payload ends in a contiguous run of
**`CommandPackage` records serialised in wire order**, running to the last byte of the
payload. The record layout is the in-memory `CommandPackage` layout, which is why the field
offsets match the ones `FUN_0094a700` prints in its `Unknown Command Packet: %d, from: %d,
size left: %d, stamp: %d` diagnostic:

| offset | size | field | evidence |
|---|---|---|---|
| `+0x00` | u32 | `stamp` | `*in_ECX` in the diagnostic |
| `+0x04` | u32 | `from` — player index | `in_ECX[1]` in the diagnostic |
| `+0x08` | u32 | (unidentified; 0 or 1 in every file seen) | — |
| `+0x0c` | u32 | **turn number** — monotone, +1 per turn | empirical |
| `+0x10` | u16 | `size` of the command body | `*(short *)(in_ECX + 4)` = byte `+0x10` |
| `+0x12` | … | body: concatenated commands | XOR-scrambled in MP, see §2 |

Header is **18 bytes**. Parsing greedily from the first record lands **exactly on the last
byte of the payload** in every file tested [measured] — a strong self-check, since a
one-byte framing error would desynchronise within a few records.

Command bodies are a concatenation of `[opcode][args]`, opcode-determined length. The
dispatch is `FUN_0094a700`, a dense `switch` over **opcodes `0x00`–`0x51` (82 command
types)**, each arm calling a handler whose **return value is the byte length consumed**
[measured]. `docs/derivation/replay-checksum-sizes` is not a separate artifact; the table is
inlined in §7 below.

Single-player `today.rcx`, reproduced fully [measured]:

- 10,541 records, **one package per turn, `from`=0 only**. The two AI opponents emit no
  packages at all — their orders are generated by the local sim, not transmitted.
- 10,532 clean turns, turn `13`…`10544`.
- **All 10,532 bodies parse to the byte with the size table** — 0 residue, 0 failures.
- Opcodes present: `0x00`:63, `0x07`:2, `0x18`:42, `0x19`:18, `0x20`:1, `0x36`:6,
  **`0x48`:10,489**, `0x4f`:1,311. `0x48` is 10 bytes and appears once per turn — it is
  `process_camera` (`zoom: %d x_loc: %d y_loc: %d` at `0x00afba70`), i.e. the replay records
  the *camera* every turn so playback can follow it.
- Max body size **51 bytes**. A `check_sums` command is 65. It cannot fit, and it is not there.

## 2. Multiplayer bodies are XOR-obfuscated

`CommandPackage::process` = **`FUN_0094c500`** (`0x0094c500`) [measured]. Before dispatching
commands it does:

```
key   = (u16)(*(u32*)([0x00c061ec] + 0x10) >> 8)
words = size / 2                       ; size is the u16 at pkg+0x10
for i in 0..words:  *(u16*)(pkg + 0x12 + 2*i) ^= key
```

gated on `[[0x00c061ec] + 0x820] & 4` — **the same flag that gates checksum emission** (§4).
An odd `size` leaves the final byte untouched.

Empirically [measured]: the recorded body is stored **scrambled**, and the 18-byte header is
**not** scrambled. Recovered keys, one per game:

| file | build | key |
|---|---|---|
| `today.rcx` (solo) | 00.2024.06.20 | `0x0000` (no obfuscation) |
| MP 2025.02.10 | 00.2024.06.20 | `0x00c9` |
| MP 2024.04.10 | 00.2017.11.29 | `0x0452` |
| MP 2024.02.23 | 00.2017.11.29 | `0xbb97` |

The key recovers trivially: it is the **most common u16 word** across bodies, because
plaintext bodies are full of zero words.

## 3. The `check_sums` command — 65 bytes, and the sixteenth word

Opcode **`0x39`**. `FUN_0094a700` case `0x39` → `FUN_009459d0` = `process_check_sums`
(`commandpackage.cpp`) [measured], which ends:

```c
FUN_00463930(..., L"  script_run_time: %u", param_1 + 0x39);
(&DAT_00cbee90)[*(int *)(in_ECX + 4)] = *(undefined4 *)(param_1 + 0x3d);
return 0x41;
```

So the handler reads a **sixteenth** `u32` at `+0x3d` and stores it per-player into
`DAT_00cbee90`, and reports **`0x41` = 65** bytes consumed.

Confirmed on the send side by disassembly at `0x009409cd`–`0x009409fb` [measured]:

```
009409e2  call 0x9c41a0            ; script_run_time channel walker
009409e7  mov  eax, [ebp-0x14]     ; its adler-32
009409ed  mov  [ebp-0x37], eax     ; field 15  -> packet +0x39
009409f0  add  eax, esi            ; esi = running sum of channels 1..14
009409f2  mov  [ebp-0x33], eax     ; field 16  -> packet +0x3d  == TOTAL
009409f5  lea  eax, [ebp-0x70]     ; packet base (opcode byte, set to 0x39 at 0x00940795)
009409f8  push 0x41                ; 65 bytes
009409fa  push eax
009409fb  call 0x94bae0            ; append command to outgoing package
```

`[ebp-0x70] … [ebp-0x2f]` is `0x41` bytes. Final layout:

| offset | field | | offset | field |
|---|---|---|---|---|
| `+0x00` | opcode `0x39` | | `+0x21` | `cities` |
| `+0x01` | `units` | | `+0x25` | `items` |
| `+0x05` | `builds` | | `+0x29` | `goods` |
| `+0x09` | `walls` | | `+0x2d` | `world` |
| `+0x0d` | `ammo` | | `+0x31` | `rules` |
| `+0x11` | `deaths` | | `+0x35` | `scenario_data` |
| `+0x15` | `groups` | | `+0x39` | `script_run_time` |
| `+0x19` | `guys` | | **`+0x3d`** | **`total` = Σ of the 15, mod 2³²** |
| `+0x1d` | `leaders` | | | **total size `0x41` = 65 B** |

Sixteen unaligned little-endian `u32` after a one-byte opcode. **`docs/derivation/checksum.md`
§4 says "total size `0x3d` = 61 bytes" — that is wrong by one field and should be corrected.**

The `total == Σ(15)` relation is what makes the packet findable without any framing at all:
the false-positive rate is ≈2⁻³², and it held for **54,947 / 54,947** packets [measured].

## 4. Why single-player replays have none

The packet builder is **`FUN_00940770`** (`0x00940770`), newly located this lane [measured].
Its gate, straight from the disassembly:

```
0094078b  mov   edx, [0xc061ec]
00940795  mov   byte [ebp-0x70], 0x39      ; opcode
00940799  mov   al, [edx + 0x820]
0094079f  test  al, 0x10
009407a1  jne   skip                        ; bit 0x10 must be CLEAR
009407a7  test  al, 4
009407a9  je    skip                        ; bit 0x04 must be SET
009407af  mov   eax, [0xc06210]
009407b7  imul  eax, [eax + 0x2a0], 0x8c    ; local player index
009407c3  movzx eax, word [edx + 0x44 + eax + 0x30]
009407c7  test  al, 1     / je  skip        ; per-player bit 0x0001 set
009407cf  test  eax,0x100 / jne skip        ; per-player bit 0x0100 clear
009407da  test  al, 0xd0  / jne skip        ; per-player bits 0xd0 clear
009407e2  call  0x6edb90 / test eax,eax / je skip
```

**Bit `0x04` of the byte at `[[0x00c061ec] + 0x820]` is the network-game flag**, and it is the
*same* bit that enables the XOR scrambling in `FUN_0094c500`. That single fact explains the
whole observation: MP replays are both scrambled and checksummed; solo replays are neither.

It then walks the fifteen channels in `check_all`'s exact order and appends the packet:

| # | channel | walker called by `FUN_00940770` | matches `check_all` |
|---|---|---|---|
| 1 | `units` | `0x009371d0` | ✔ |
| 2 | `builds` | `0x00937290` | ✔ |
| 3 | `walls` | `0x00937360` | ✔ |
| 4 | `ammo` | `0x009374e0` | ✔ |
| 5 | `deaths` | `0x00936bb0` | ✔ |
| 6 | `groups` | `0x00937530` | ✔ |
| 7 | `guys` | `0x00937430` | ✔ |
| 8 | `leaders` | **`0x009375a0`** | `check_all` inlines the 8× `0x006d6750` loop; the sender uses this helper |
| 9 | `cities` | `0x00937600` | ✔ |
| 10 | `items` | `0x00937790` | ✔ |
| 11 | `goods` | `0x00937710` | ✔ |
| 12 | `world` | `0x006b5cf0(w,-1)`, **conditional** on `[[0x00c06188]+0x134] != 0`; otherwise the field is left at `1` | ✔ same condition |
| 13 | `rules` | `0x00589550` | ✔ |
| 14 | `scenario_data` | `0x00997ad0` | ✔ |
| 15 | `script_run_time` | `0x009c41a0` | ✔ |

**Cadence.** `FUN_00940770` has exactly one caller: `FUN_0093ef10` (`commandmanager.cpp`, the
`PROCESS_TURN` path), `call 0x940770` at **`0x0093f2e9`** [measured], with **no frame divisor** —
all gating is the flag test above. Hence one checksum per player per turn, which is exactly
what the corpus shows. `CheckDesyncsEveryXFrames` belongs to the separate `Skybox_SyncLogger`
subsystem (§6) and does **not** throttle this path.

## 6. If you need this in single-player: the `synclogger.ini` route

`FUN_00a30080` (`Skybox_SyncLogger.cpp`) reads **`.\synclogger.ini`**, section
**`[Settings]`** [measured, re-derived independently this lane]. The two UTF-16 literals are
loaded at `0x00a301d6` (`mov [ebp-0x70], 0xb18294` = `Settings`) and `0x00a30206`
(`mov [ebp-0x5c], 0xb182dc` = `.\synclogger.ini`). Keys read there, each with a string
default:

| key | pointer global | default |
|---|---|---|
| `StartLoggingOnWorldTimeMS` | inline literal | — (stored to `this+0xa8`) |
| `DesyncTrackingEnabled` | `0x00c0666c` | `"0"` |
| `DesyncUploadsWanted` | `0x00c06664` | |
| `DesyncTrackingFrameHistorySize` | `0x00c06668` | |
| `CheckDesyncsEveryXFrames` | `0x00c06674` | |
| `SkipCountdown` | `0x00c06670` | |

`.\` means the file goes next to `riseofnations.exe`, i.e.
`C:\Program Files (x86)\Steam\steamapps\common\Rise of Nations\synclogger.ini`. **No
`synclogger.ini` and no `SyncLog*` files currently exist in that directory** [measured, live
`Get-ChildItem`].

**I did not establish that this produces the fifteen `check_all` channels in single-player.**
`Skybox_SyncLogger` is a different subsystem with its own 38-category table at `0x00c06370`
(a superset of the checksum channels — it has `Terrain`, `Pathfinder`, `Animals`, `Sound`,
which `check_all` does not). Its output is `SyncLog %s %s.txt` with `BEGIN TURN %06u` banners.
Whether those banners carry the `CheckSum` walk or only category traces is untested. Testing
it is cheap and is the obvious next step — drop the ini, restart the game, play thirty
seconds of skirmish, look at the file — but it requires restarting the game and the user was
playing.

**For our purposes it may not matter.** A multiplayer replay is a *better* oracle than a
single-player one anyway: it has two independent players' checksums per turn, which lets us
distinguish "our sim is wrong" from "the checksum is nondeterministic".


`0x40 & 0x04 == 0` — **the network-game bit is clear**, so `FUN_00940770` is skipping the
checksum send, and correspondingly the received-`total` array `DAT_00cbee90` stays at zero and
does not advance. That is the §4 gate confirmed against a live process, not just decompiled C.

## 8. Reproduction

Extractor (framing + XOR + structural checksum test). Runs on any `.rcx`:

```python
import zlib, struct, collections
HDR = 18
SZ = {0:None,1:1,2:5,3:0xd,4:0x11,5:0xd,6:0x11,7:0x16,8:0x1a,9:10,0xa:10,0xb:0x19,
 0xc:1,0xd:1,0xe:5,0xf:9,0x10:0xd,0x11:0x15,0x12:9,0x13:9,0x14:0xd,0x15:5,0x16:0x11,
 0x17:0x15,0x18:9,0x19:0x19,0x1a:0x11,0x1b:1,0x1c:0x19,0x1d:1,0x1e:0xd,0x1f:0xd,
 0x20:9,0x21:9,0x22:0x19,0x23:1,0x24:1,0x25:0xd,0x26:0xd,0x27:9,0x28:9,0x29:9,0x2a:9,
 0x2b:0x11,0x2c:0x11,0x2d:0x11,0x2e:0xd,0x2f:0xd,0x30:0xf,0x31:0xb,0x32:9,0x33:None,
 0x34:5,0x35:1,0x36:1,0x37:1,0x38:5,0x39:0x41,0x3a:6,0x3b:5,0x3c:5,0x3d:5,0x3e:1,
 0x3f:1,0x40:1,0x41:5,0x42:5,0x43:0x11,0x44:None,0x45:9,0x46:5,0x47:7,0x48:10,
 0x49:0x21,0x4a:0xb,0x4b:0x35,0x4c:2,0x4d:2,0x4e:0x209,0x4f:9,0x50:3,0x51:2}
CH = ["units","builds","walls","ammo","deaths","groups","guys","leaders","cities",
      "items","goods","world","rules","scenario_data","script_run_time"]

def load(p): return zlib.decompress(open(p,'rb').read(), 16+zlib.MAX_WBITS)

def parse_from(d, o):
    n=len(d); recs=[]
    while o+HDR<=n:
        sz=struct.unpack_from("<H",d,o+16)[0]
        if o+HDR+sz>n: break
        st,fr,c,tn=struct.unpack_from("<IIII",d,o)
        recs.append((o,st,fr,c,tn,sz,d[o+HDR:o+HDR+sz])); o+=HDR+sz
    return recs,o

def find_stream(d):
    """Earliest offset that (a) chains record-by-record to exactly EOF and
       (b) shows a period-P turn counter incrementing by 1."""
    n=len(d); reach=bytearray(n+1); reach[n]=1
    for o in range(n-HDR,-1,-1):
        sz=struct.unpack_from("<H",d,o+16)[0]; nx=o+HDR+sz
        if sz<8192 and nx<=n and reach[nx]: reach[o]=1
    for o in range(n-HDR):
        if not reach[o]: continue
        if struct.unpack_from("<H",d,o+16)[0]>1024: continue
        if not 1<=struct.unpack_from("<I",d,o+12)[0]<=64: continue
        recs,_=parse_from(d,o)
        if len(recs)<200: continue
        for P in range(1,9):
            t=[r[4] for r in recs[::P]]
            if len(t)>=80 and sum(t[i+1]==t[i]+1 for i in range(len(t)-1))>0.9*(len(t)-1):
                return o,P,recs
    return None

def detect_key(recs):
    wc=collections.Counter()
    for r in recs:
        b=r[6]
        for i in range(0,len(b)-1,2): wc[struct.unpack_from("<H",b,i)[0]]+=1
    return wc.most_common(1)[0][0] if wc else 0

def dexor(b,k):
    if not k: return b
    out=bytearray(b)
    for i in range(0,len(b)-1,2):
        struct.pack_into("<H",out,i, struct.unpack_from("<H",out,i)[0]^k)
    return bytes(out)

def checksums(path):
    """-> {turn: {player: [15 channels] + [total]}}"""
    d=load(path); r=find_stream(d)
    if not r: return {}
    _,_,recs=r; key=detect_key(recs); out={}
    for rec in recs:
        if rec[2]>=16: continue                      # sane 'from'
        b=dexor(rec[6],key)
        for p in range(0,max(0,len(b)-64)):
            if b[p]!=0x39: continue
            v=list(struct.unpack_from("<16I",b,p+1))
            if (sum(v[:15])&0xffffffff)!=v[15]: continue
            if not all((x&0xffff)<65521 and (x>>16)<65521 for x in v[:15]): continue
            out.setdefault(rec[4],{})[rec[2]]=v
            break
    return out
```

## 9. What this buys us, concretely

1. **A per-turn, 15-channel differential oracle with zero instrumentation.** Feed our Rust
   sim the command stream from a multiplayer `.rcx`; at each turn compute our own `DataWalk`
   adler-32 per channel and compare against the recorded 16-tuple. The first mismatching turn
   *and channel* is the bug. This is the validation harness `docs/CHARTER.md` stage 6 asks for,
   and it costs a parser rather than an emulator.
2. **A bisect that is already sorted.** Channels are independent, so a mismatch in `units`
   with `world` still matching says the terrain/fog path is fine and the unit path is not. The
   `world` channel changing every turn while `rules` never changes gives a free sanity test of
   our own walker before we ever compare to retail.
3. **`rules` = `0x12ba3104`.** A single 32-bit target the rules lane can aim at today, with no
   emulator and no oracle call, that transitively validates the entire loaded rule set's
   sim-critical bytes and their traversal order.
4. **Two independent witnesses per turn.** Both players record their own checksum. If our sim
   disagrees with *both*, we are wrong. If the two retail players ever disagree with each
   other (none did here), that turn is nondeterministic in retail and must be excluded.
5. **A corpus of ~54,900 packets already on the VM**, spanning two engine builds, and 64 more
   replays not yet extracted.

Order of work this implies: build the `.rcx` command-stream parser as a real crate artifact
(it is 100 lines), then the `DataWalk` trait in Rust mirroring §4's channel order, then
compare `rules` first (constant, cheap), then `walls`/`ammo`/`deaths` (mostly `1`), then the
per-turn channels.

## 10. What I could NOT establish

- **The size of command `0x4a`, and hence a 100% clean body parse for MP.** Solo bodies parse
  to the byte (10,532/10,532). MP bodies do not: after the `check_sums` command there is a
  consistent one-byte residue around the `0x4a` command. `FUN_00943d20` (`0x4a`) reads u16
  fields at `+1,+3,+5,+7,+9` and `FUN_0094a700` receives `0xb` = 11 from it, but the MP body
  arithmetic wants 12 in some packages and 11 in others. Either `0x4a` is 12 with a field I
  mis-read, or MP packages carry a one-byte trailer. **This does not affect any result above** —
  the checksum packets are located by the `total == Σ(15)` signature, not by walking the
  command sizes — but a later lane owning the command stream must settle it.
- **Opcode sizes for `0x33` and `0x44`.** Their handlers have no constant `return` in the
  bulk decompilation; both are absent from every replay analysed, so they never mattered here.
- **The meaning of `CommandPackage +0x08`,** and of the `stamp` field at `+0x00` (which
  advances at a different rate from the turn counter at `+0x0c`: in `today.rcx` it lags the
  turn by 1 at the start and by 44 at the end).
- **Whether `synclogger.ini` yields the fifteen `check_all` channels in single-player.** §6.
  Untested; requires restarting the game.
- **The full meaning of `[[0x00c061ec]+0x820]`.** Bit `0x04` is measured to gate both checksum
  emission and XOR scrambling, and is measured clear in the current non-network process. I am
  calling it "the network-game flag" on that evidence; I did not enumerate its other writers.
- **Any desynced replay.** 0 divergences in 27,473 comparable turns. Finding one would be the
  single most informative artifact for calibrating "how much divergence is normal".
- **Whether the initial world state is stored in the header blob or only a seed.** Out of lane;
  still open from `docs/replay-format.md`. Note the command stream begins near payload offset
  `0xf9e8c` in `today.rcx` and `0xf9eda` in the 2025 MP replay (the anchor lands a few records
  early in both; the first clean turn is 13 and 3 respectively) — **~1 MB of *something*
  precedes it in both files**, which is a strong hint that full initial state is stored rather
  than just a seed, and that the preceding blob is worth attacking with the `SaveGame`
  traversal from `docs/derivation/checksum.md` §3.
