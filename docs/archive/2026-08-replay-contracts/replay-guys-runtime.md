# Replay Guys runtime: exact recursive owner, no initial producer

Lane: `replay-guys-runtime` · replay-first Gen-8 prerequisite · 2026-08-11.

This tranche answers one bounded question: if every live Unit already has an exact
`PtrArray<Guy>` image, can replay execute the shipped Guys checksum without losing owner
order, pointer topology, allocation history, or stable identity?

`crates/don-replay/src/guys_runtime.rs` does that. It binds the existing complete
`don_sim::systems::groups_guys::UnitGuys` byte state to a generational Unit handle, resolves
that handle through `World`'s canonical sparse `(who,o)` bands, validates the array and
every non-null Guy identity, then hashes the exact retail stream. It is path-mounted only
by `crates/don-replay/tests/guys_runtime.rs`; it is not registered in the replay harness and
does not claim a recorded checksum match.

## The exact array stream

An empty array contributes only its signed four-byte zero length. Capacity, increment,
flags, and dormant pointer storage are not read, and the function returns before clearing
the flags byte.

A positive-length array contributes, in order:

| operation | bytes |
|---|---:|
| signed length | 4 |
| capacity | 4 |
| signed 16-bit increment | 2 |
| `flags & ~0x40` | 1 |
| one pointer-presence byte per logical slot | `length` |
| capacity and increment a second time | 6 |
| each non-null Guy's raw synchronized image, in slot order | `155 × non_null` |

Thus the exact length is `17 + length + 155 × non_null`. The repeated capacity/increment
range is real: the function first walks those fields individually, then walks
`[PtrArray+8,PtrArray+0xe)` after the pointer-presence pass.

The `0x40` clear on a positive-length array is also a real persistent mutation, not merely
a checksum mask. The channel adapter preflights every reached array before changing any
authority, then clears the bit on all reached positive arrays as one commit. A later invalid
Unit therefore cannot leave an earlier array half-mutated in the fail-closed host.

## Dynamic and identity boundaries

For a non-empty array the adapter refuses:

- a negative capacity or logical length above capacity;
- a negative `UnitData::guy_mark` or a mark above logical length;
- a null pointer inside the initialized squad prefix `[0,guy_mark)`;
- a non-null slot whose index cannot fit `GuyData::guy_num`; or
- any non-null Guy whose `{who,o,guy_num}` differs from its owning Unit and pointer slot.

It does not infer `squad_size` or `crew_size`. Slots after `guy_mark` can lawfully include
both the dead/uninitialized squad tail and non-null crew, and distinguishing those requires
the current `UnitTypeData` row. The exact pointer topology and every 155-byte non-null Guy
image are therefore explicit authority, not regenerated by this walker.

Authority is keyed by `{Handle.id, Handle.generation}`, never by dense row. The outer walk
validates sparse storage class, mark, tombstones/reservations, sparse identity resolution,
dense handle, `UnitData::who`, and `UnitData::o`. Tests remove an earlier dense row and prove
that the survivor retains its own Guys after compaction; stale authority for the removed
generation is refused.

## Driver correction: Guys reaches owner 8

The shipped loop bound is exactly nine records:

```text
(0x00e789dc - 0x00e3a390) / 0x6eec = 9
```

Guys therefore reaches owner slots `0..=8` in fixed order. Owner 9 participates in normal
object processing but is outside this checksum. This agrees with `don-replay::state` and
`check_all` and with the independently derived Units runtime.

`don_sim::systems::groups_guys::check_guys` now keeps this boundary explicit with
`GUYS_CHANNEL_OWNER_SLOTS = 9`, separate from the eight Group/playable owners. Its owner
bands and leader gate reach owner 8 without widening Group allocation, processing, or the
eight-word `last_group` tail.

## Corpus deadline, not a fitted input

The local scan found 63 `.rcx` files: 61 decode under the current reader and two legacy
files fail obfuscation-key recovery. The 61-recording decoded corpus contains 21
checksum-bearing recordings and 222,938 Guys comparisons. Every first checkpoint is
non-vacuous, and all 21 first Guys values are distinct. The test checks only those
structural facts. No target checksum is passed into the adapter, no partial image is
compared with a final word, and no byte is selected to improve agreement.

This records the deadline: recording-specific Guy state already exists at the first
checksummed turn. It is not evidence that any current replay producer can build that state.

## Why first-turn installation is still unlawful

The checksum traversal is complete, but the state producer is not. Installation requires
all of these in one setup transaction:

1. **Starting-Unit schedule and identity.** Replay still stops before the exact
   `Setup::build_game -> Setup::build_empire -> Setup::build_units` path. The unresolved
   player/team-to-start-index schedule determines which types and coordinates are created.
2. **One complete `Objects::init_unit` owner.** The existing
   `objects_init_unit_authority_frontier` validates receipts but explicitly does not own
   sparse reuse, full `Unit::init`, linked members, leader accounting, nearby placement,
   or every RNG transition.
3. **Current type facts.** Guy allocation needs `UnitTypeData::squad_size + crew_size` and
   the squad/crew boundary. `squad_size` at `+0x304` is not supplied by `unitrules.xml`; the
   existing mechanics report leaves its `UnitType::init` binding open. Replay has no
   canonical current-type owner exposed to this channel.
4. **`Guy::clear` and `Guy::init_real`.** `UnitGuys::spawn_full` is a semantic helper, not
   the retail constructor image. Retail clear starts fields such as type, coordinates,
   `ox`, `whom`, and `gpiece` at non-zero sentinels, and `init_real` consumes
   `game_random` once to choose initial `cur_anim` before validating the loaded animation
   packet. Those values lie inside the 155-byte checksum window.
5. **Graphics hierarchy materialization.** `graphics_turret` has an exact fail-closed
   extractor boundary for gpiece, track offsets, pivot angles/flags, and graph identity,
   but replay has no loaded `.bh3` hierarchy provider. Crew placement recursively uses
   those graphics-derived track offsets.
6. **Persistent dynamic ownership.** Normal `World`/`Sim::spawn_unit` writes a synthetic
   scalar `guy_mark = 1` and allocates no `UnitGuys`. `Sim::crash_units` can hold optional
   row-keyed Guys for one aircraft-crash path; it is neither generational checksum
   authority nor part of canonical save/replay state.

Until all six are owned, a harness hook would either hash no Guys or fill synchronized bytes
with plausible defaults. Both would be a false compatibility claim. The next lawful step is
to make the complete shared `Objects::init_unit` transaction produce an identity-bound
`UnitGuys` plus graphics binding, then register this module with one `pub mod
guys_runtime;` line and install the direct channel only after replay setup reaches that
producer.

## Focused evidence and level

The focused suite freezes:

- exact empty and non-empty stream order, duplicate history, null topology, and 155-byte
  recursion;
- agreement with the independently landed `UnitGuys::walk` on the same input;
- impossible container and per-Guy identity refusal;
- fixed owner-major order, explicit owner-8 inclusion, and owner-9 exclusion;
- stable authority through dense compaction and stale-generation refusal;
- inactive driver/leader/object gates;
- atomic `0x40` commit behavior; and
- the current World's missing Guys owner plus the full local corpus deadline.

This is instruction-derived structural ownership with source tests. It has no injected
retail differential and no installed replay producer, so it promotes no fidelity tier and
claims zero recorded channel matches.
