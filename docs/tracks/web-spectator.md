# Track: web-spectator — a browser spectator running the **real** rules

**Lane: `web-spectator`.** This is engineering and measurement on top of other lanes'
derivations. It derives nothing itself; what it does is *compose* the derived damage chain,
the live unit-type table, the live balance table and the live combat constants into
something that runs at 120 fps in a browser tab and that a person can click on.

Every claim is **[measured]** (I ran it on this machine and the artefact is in-repo) or
**[reported]** (I read it and have not checked it). Fidelity tiers belong to the pieces
this lane consumes, not to this lane: `don_sim::damage` is Tier B because the combat lane
tested it against retail; the glue around it here is a **placeholder** and is labelled as
such at every site.

## 0. Headline

**The page now simulates real Rise of Nations unit types fighting through the derived
`ObjectData::get_damage` chain, and it holds this display's full 120 fps while doing it —
at 4,096 units in one world, and at 4,096 worlds × 64 units (262,144 units) with the
simulation on eight workers.** [measured]

Three numbers that say what changed since the last round:

| | last round (placeholder mechanics) | this round (real tables + derived damage) |
|---|---:|---:|
| what a unit is | one of one kind, random stats | one of **190 roster types** out of the live `UnitType` list, with its real `HITS`/`ATTACK`/`ARMOR`/`MOVES`/`MAX_RANGE`/`RECHARGE`/`OBJ_MASK` |
| what a hit is | nothing; units never fought | `don_sim::damage`, the 31-step integer chain at `0x00644130`, with `Balance::final_balance_table[atk][def]` and the live `Constants` combat values |

simulation are on different threads and the display is the binding constraint.

And the check that could have failed and did not:

## 1. What is real on this page, and what is not

This is the section to read before believing anything on the screen. It is also the section
that took the most care to get right, because a spectator showing the *real* balance table
through a *placeholder* engagement loop is exactly the kind of thing that gets remembered
as "we simulated Rise of Nations in a browser".

### 1.1 Derived, and used unmodified

| what | where it comes from |
|---|---|
| the damage arithmetic | `don_sim::damage` — `ObjectData::get_damage` `0x00644130`, all 31 steps, **Tier B** (the combat lane's differential testing, not mine) |
| the attack/armor getters | `don_sim::get_attack` / `get_armor` — `0x006469F0` / `0x00647DB0` |
| the balance index | `don_sim::balance_index`, and the base shift the derivation records (row 0 is type id 50) |
| the flank tier | `don_sim::flank_level` `0x0092CFE0`, reached from inside step 20 |
| 364 unit types | `schema/live/live-tables-unit.tsv` — the live `UnitType` list at `0x00C0A264` |
| the 493×493 balance table | `schema/live/balance-real.bin` — `Balance::final_balance_table` at `0x00C12BF4`. The page shows its **367 distinct values** as a badge, so "real data" is a claim it can back up rather than assert |
| 16 combat constants | `schema/live/rules-block-pid14644.txt`, the live `Constants` singleton at `+0x44…+0xB98`. `FLANK_BONUS` 50, `ROCKY_MODIFIER` 170/256, `RIVER_MODIFIER` 512/256, `OVERKILL_FRAMES` 30, … |
| the frame scheduler's order | `Objects::process_all` rotates owner slots `(frame + i) % 10`. Reproduced, because a fixed-order scheduler diverges inside one tick |
| the RNG recurrence | `s ← s·1664525 + 1013904223`, `Random::get` |
| the tick period | 67 ms at Normal (`TurnControl::timings` `0x00AFC4A4`), which the UI states — **not** 15 Hz |
| the command wire format | `schema/command-wire.json`, all 82 opcodes, **code-generated** into both the JS encoder and the Rust decoder (§4) |

### 1.2 Placeholders, every one of them mine

* **Target acquisition** — nearest enemy in a local grid neighbourhood, else march on the
  nearest enemy owner's centroid. The engine's acquisition is in `Unit`/`Order` code nobody
  has read.
* **Movement** — one integer step of `MOVES` subtiles along the straight line to the goal.
  No pathfinder, no terrain, no collision, no formation.
* **The attack angle** — an integer `atan2` written for this file. The *consumer* (the
  flank tier and the `FLANK_BONUS` arithmetic) is derived; the producer is not.
* **The damage predicates** — the chain reads about thirty booleans obtained by walking an
  object graph that does not exist here. Exactly two are set: attacker alive and defender
  alive. Everything else is left **false**, which is the inert value: with this set the
  chain reduces to `((attack × balance / 100) [+ flank] + 5) / 10 − armor`, floored at 1
  when the floor's own three conditions hold. Setting `attacker_vf_0x20` and
  `defender_vf_0x20` true would multiply damage by four (step 5) — that is precisely the
  guess this project exists not to make.
* **`MOVES`'s unit** is not derived. It is used here as subtiles (1/192 tile) per frame,
  which is consistent with the rules.xml denominator of 192 and is otherwise an assumption.
* **No terrain, height, buildings, economy, line of sight, upgrades, or population caps.**
* **The arena** — 128 tiles, armies starting a third of a map apart, battles restarting
  when one side is wiped. Staging decisions, so a cluster keeps moving and a battle is
  watchable within seconds rather than minutes.

So: the *arithmetic* of a hit is the engine's, the numbers going into it are the engine's,
and the decision of who hits whom is mine. `web/wasm/src/real.rs` says this at the top of
the file, and `web/README.md` says it again.

### 1.3 Real damage, printed

`cargo run --release --bin digest -- damage <atk> <def>` runs the chain outside the browser
so any number on screen can be checked without one. [measured]

```
Knight(228) -> Tank(244)     attack_x10=160 armor=6 balance=100%  -> 11   flank_tier=1
Tank(244)   -> Knight(228)   attack_x10=200 armor=4 balance=184%  -> 35   flank_tier=1
Catapult(265) -> Knight(228) attack_x10=170 armor=4 balance=100%  -> 14   flank_tier=1
```

Tanks hit cavalry for 184% and cavalry hit tanks for 100%: that asymmetry is the shipped
balance table, not something this lane chose.

**A finding for the combat lane.** With the defender facing angle 0, an `attack_dir` of 0
scores flank tier **1** and an `attack_dir` half a turn away scores tier **0** — because
step 20 biases the delta by `0x80000000` before testing it. Whatever `attack_dir` means
geometrically in retail, "the direction the attack comes from, and behind is a flank" is
not obviously it. The `digest damage` output deliberately labels the two cases by their raw
angles rather than "front"/"back" for that reason. Not resolved here.

## 2. Architecture, and what this round changed

The data path is the previous round's and it survived contact with a real simulation intact:
`don-sim`-shaped structure-of-arrays columns are bound **directly** as per-instance vertex
buffers, so there is no interleaved instance struct, no repack pass, no `f32` conversion,
and no per-entity CPU loop anywhere in the system. `docs/tracks/web-frontend.md` §2 argues
that design; it is unchanged and still correct.

What this round changed:

1. **A third per-frame upload.** The per-instance `tag` used to carry owner and occupancy
   only, so it changed on population change and rode a dirty flag. It now carries **hit
   points**, so every hit changes it and it is uploaded every frame like the positions. The
   cost is measured, not waved away: at 262,144 instances the three-column upload is 1.19 ms
   against the two-column 0.84 ms of the previous round — about **0.35 ms for the third
   column**, and it buys per-unit health shading, per-type hue, and the selection highlight
   with zero CPU work (§5.2).
2. **The tag is written by the simulation, not by JavaScript.** `RealWorld::refresh_tags`
   packs the whole per-instance appearance into one `u32` at the end of each tick, so the
   zero-copy path still binds the world's own allocation and the alternative — a JS loop
   over every entity every frame — never exists.
3. **Eight stats per world instead of four**, read by the aggregate shader as two `vec4u`
   out of one 32-byte-stride instance buffer: population, hit points, digest, frame, kills,
   damage, rounds, sides-alive. Five selectable metrics instead of two. Adding metrics costs
   a wider stride and nothing else.
4. **Commands are real engine packets** (§4), which replaced the previous round's invented
   `Order` envelope.
5. **Game data is fetched once and staged into wasm before `sim_create`**, which is also
   the only allocation that can grow linear memory and detach a view. A checkout without
   `schema/live/` runs a synthetic table and says so in a red badge.

## 3. The cluster view

A grid of world viewports, one instanced draw for all of them, plus an aggregate mosaic
above the readability threshold — that is the previous round's design and it still holds.
Two things are new and both matter for watching a training run:

* **Five aggregate metrics.** Population is degenerate while every world is full; the
  digest fingerprint shows *divergence*; army hit points and kills show *how the fight is
  going*; sides-alive shows *which worlds are over*. The shader picks on three uniform bits,
  so the choice costs nothing.
* **A statistics strip** under the mosaic (2D canvas, main thread, 2 Hz): live units, army
  hit points, cumulative kills and battles fought across the whole cluster, as sparklines.
  The mosaic answers "which world is different"; this answers "what is the cluster doing".
  At 2 Hz it cannot compete with the renderer for anything.

Screenshots are producible from the page itself — `await window.don.snapshot()` returns a
base64 PNG of exactly what the renderer drew. That function exists because of §7.1.

## 4. Drop in and play: the browser speaks the engine's command format

This is the part of the brief that went furthest beyond last round. The page no longer
carries an invented order record. It carries **the engine's packets**.

### 4.1 Generated, not transcribed

`web/tools/gen-wire.mjs` reads `schema/command-wire.json` — 82 opcodes, 224 fields, derived
by the `headless-client` lane from `rise.pdb` and cross-checked against
`CommandPackage::process` — and emits **both** sides of the codec:

* `web/public/js/wire.gen.js` — the browser's encoder/decoder.
* `web/wasm/src/wire_gen.rs` — the wasm decoder, with a reader per field this simulation
  can honour and none for the fields it cannot.

Neither side of this app contains a hand-written byte offset. A change to the derived JSON
changes both.

Field *widths* are not in the JSON, only offsets and type names. Every command struct is
packed and every field is listed in offset order, so a field's width is the next field's
offset minus its own and the last field's width is the wire size minus its offset. That
reconstructs `QueuePos`, `OrderIndex`, `Coord` and the rest exactly, without guessing.

### 4.2 What a click becomes

```
pointerup  ->  render worker inverts the camera            -> (world, subtile x, subtile y)
           ->  a *query* to the worker that owns that world -> object ids near the point
           ->  GroupCommand 0x00 encoded here, bytes posted to that worker
           ->  MoveToCommand 0x07 / AttackCommand 0x04 / HaltCommand 0x0c, same route
           ->  decoded in Rust at the derived offsets, drained at the tick boundary
```

Left click selects, right click moves, shift+right click attacks the unit under the cursor,
and the panel prints the packet — `0x00 GroupCommand — 255 units, who=0, 513 B`. A
`MoveToCommand` is 22 bytes and the page hex-dumps it on demand:
`07 39 30 00 00 d6 ff ff ff 00 00 00 00 00 00 00 00 00 01 03 00 00`.

Selection being its own command is a fact about the action space, not a UI convenience: the
engine's orders apply to the current group, so an RL action space that emits one command per
unit is modelling a different game.

### 4.3 Two findings about the action space

**`GroupCommand` names at most 255 objects**, because `num` is an `unsigned char`
[measured, from the derived field types]. Selecting a 400-unit army is therefore *not* one
`GroupCommand`, and how the engine does it is not derived. The page truncates and says so
rather than feeding 400 ids into a `u8` count.

**A `GroupCommand` list entry is a 2-byte object index.** `schema/command-wire.json` gives
the entry type as `GroupCommand::<unnamed-type-list>[2]` inside a struct whose declared wire
size is 5 — which does not add up until you look at the type record:

```
llvm-pdbutil dump --types ron-bin/sbl/rise.pdb
  0x11957 | LF_STRUCTURE `GroupCommand::<unnamed-type-list>`  sizeof 2
             - LF_MEMBER [name = `o`, Type = short, offset = 0]
```

So an entry is `struct { short o; }`, the packet is `3 + 2·num` bytes, and the declared size
5 is the **one-entry** case. That resolves an ambiguity the JSON alone cannot, and it is now
in the generator's comments and in the Rust decoder. [measured]

### 4.4 The same action space `don-env` uses — cross-checked

While this lane was running, another lane built `crates/don-env`, whose action space is
generated from the *same* `schema/command-wire.json`. That makes an independent check
possible, so I ran one: every opcode `don-env`'s `VERBS` table declares that this page's
codec also knows — **49 opcodes** — agrees on wire size, `MOVE_TO` at 22 bytes and `ATTACK`
at 17 included. [measured]

```sh
node -e "…compare crates/don-env/src/generated.rs against web/public/js/wire.gen.js…"
# opcodes cross-checked: 49    all wire sizes agree
```

Two independent generators, one derived source, no disagreement. That is what makes "a
human clicking and a policy acting emit the same bytes" a checkable statement rather than
an aspiration. `don-env` additionally records which fields each verb leaves *unsupplied*
(`MOVE_TO`: `set_angle`, `angle`, `width`, `disembark`) — the same subset this page
declines to model, arrived at separately.

### 4.5 What is honoured, and what is not

`MoveToCommand` has nine fields; this simulation honours `to_x` and `to_y`. `set_angle`,
`angle`, `orders`, `queued`, `form`, `width` and `disembark` are written as zero and
ignored, because placeholder movement has nothing for them to mean and inventing values
would be worse than leaving them out. Both the Rust and the JS say exactly that at the
definition site.

`who` comes from the transport, not the packet — in the engine the command stream is
per-player and the body carries only the command's own fields. `GroupCommand` is the
exception (it names its player) and the dispatcher honours that.

simulation is what makes the architecture earn its keep.

### 5.3 Where the simulation's time actually goes

Simulation only — no uploads, no draws (`bench('sim-only')`), and the native twin for
comparison. [measured]

| configuration | wasm step ms | native step ms | native M unit-steps/s |
|---|---:|---:|---:|
| 1 world × 2 × 64 | 0.009 | 0.004 | 28.3 |
| 1 world × 2 × 256 | — | 0.059 | 8.0 |
| 1 world × 2 × 512 | 0.111 | 0.137 | 6.3 |
| 1 world × 2 × 1,024 | — | 0.924 | 1.7 |
| 1 world × 2 × 2,048 | 0.951 | 3.416 | 0.9 |
| 64 worlds × 2 × 64 | 0.236 | 0.232 | 14.9 |
| 1,024 worlds × 2 × 32 | 1.778 | 5.740 | 9.6 |
| 4,096 worlds × 2 × 32 | — | 19.803 | 11.1 |

Two things to read out of this, and one not to.

**Throughput collapses as a world gets dense**: 28.3 M unit-steps/s at 128 units in a world,
0.9 M at 4,096 — a 30× fall for 32× the units, i.e. *quadratic*. The damage chain is O(1)
per attack, so that is not the damage chain. It is **target acquisition**: the local grid
scan is capped at 192 candidates per acquisition, and a re-acquisition happens whenever a
unit's target dies — which, in a dense melee, is constantly. Spreading the same units over
64 worlds instead of one costs 16× less per unit-step. **The acquisition scan is the thing
to fix**, not the arithmetic, and that is the opposite of what I expected before measuring.

**Do not read a wasm-versus-native ratio out of that table.** The two are not measuring the
same state: the native benchmark starts a fresh battle and measures 120 frames while armies
are still marching (every unit re-acquiring every frame), and the browser measures a battle
that has been running for seconds. The rows where they happen to agree (64 worlds × 64
units: 0.236 vs 0.232 ms) and the rows where they differ by 3.6× are both explained by that,
not by codegen. What this table supports is exactly one claim: wasm and native are in the
same order of magnitude on this workload.

**This is the axis frame rate cannot see.** 1,024 worlds × 64 units, read from the shards'

| sim workers | M unit-steps/s | world-steps/s | speed-up | × real time, per world |
|---:|---:|---:|---:|---:|

**A browser tab runs 1,024 simultaneous battles at 183× real time each, while rendering all

Measuring this with fps would have reported a 1.01× "speed-up" (the `shards` sweep in

does not work. It is the wrong instrument and it gives the wrong answer by 6×.

### 5.6 WebGL2 fallback

The fallback carries the same architecture — integer instance attributes via
`vertexAttribIPointer` + `vertexAttribDivisor`, one draw call, the same tag unpacking in

queries on this path and `gl.finish()` is not a GPU fence in Chrome, so an uncapped number
there would be an artefact. Forced with `?backend=webgl2`.

## 6. Cross-target determinism — the check that could have failed

4 worlds × 2 sides × 64 units, capacity 128, seed `0xC0FFEE`, exactly 600 frames of real
combat:

| build | digest | kills | damage | live |
|---|---|---:|---:|---:|
| aarch64-apple-darwin (`digest 4 2 64 128 600 0xC0FFEE`) | `0xb0b359aba78793c2` | 550 | 75,071 | 324 |
| wasm32-unknown-unknown in Chrome (`window.don.stepFrames(600)`) | `b0b359aba78793c2` | 550 | 75,071 | 324 |

**Identical**, over roughly 150,000 unit-frames including 550 deaths, 550 row compactions,
and the whole derived damage chain. Two independently compiled targets — one where LLVM
autovectorises freely, one where it does not — agree on a 64-bit digest, and they agree on
the three quantities the digest is *not* directly made of. It re-runs in one command, it
would fail loudly, and it is the precondition for a spectator being worth looking at.

It also caught a mistake once already: an earlier native run disagreed, and the reason was
that I had changed the spawn geometry between the two runs. The check works.

## 7. What went wrong, and what it cost

### 7.1 A deleted fragment shader rendered nothing, silently, and three different screenshots agreed it was fine

A refactor of the WGSL vertex stage removed `fs_units` along with it. The consequences,
in order:

* `createShaderModule` **succeeded** — the module is valid WGSL; the entry point simply is
  not there.
* `createRenderPipeline` **returned a pipeline object** rather than throwing. WebGPU
  validation failures are not exceptions.
* Every `pass.draw` with that pipeline was **silently dropped**. Canvas: black.
* `Page.captureScreenshot` over CDP returned a transparent rectangle where the
  GPU-composited OffscreenCanvas was — which looks exactly like a renderer that drew
  nothing, *and would have looked exactly like that even if the renderer were fine*.
* `canvas.convertToBlob()` after present returned a uniformly black image. Same.
* Copying from `getCurrentTexture()` after `submit` returned uniformly black. Same again —
  the texture has already gone to the compositor.

Four independent signals all said "black" and none of them said "why". What broke the tie
was running the **WebGL2** backend and calling `gl.readPixels`, which showed the picture —
proving the geometry, the tag unpacking and the colours were all correct and the fault was
in WebGPU. The actual error only became visible after wrapping each `createRenderPipeline`
in `device.pushErrorScope('validation')`:

```
units pipeline: Entry point "fs_units" doesn't exist in the shader module.
```

Three things are now permanent so this cannot recur silently:

1. `device.addEventListener('uncapturederror', …)` and `module.getCompilationInfo()`, with
   any diagnostics carried up to the page and printed in red in the log.
2. An error scope around every pipeline creation, reported the same way.
3. `backend.readback(drawAgain)` on **both** backends, which re-renders the frame into a
   texture the backend owns and copies it back — the only capture that tells the truth —
   exposed as `window.don.snapshot()`, and reporting a non-black pixel count so "0 non-black
   pixels" is a fact rather than an impression.

The general lesson, and it is not WebGPU-specific: **an API whose failures are events rather
than exceptions needs its failure channel wired up before you trust any of its successes.**

### 7.2 A transferred buffer reports length 0

`postMessage(msg, [bytes.buffer])` detaches the buffer, so `bytes.length` afterwards is 0 —
and the command log cheerfully reported `GroupCommand … 0 B` for a packet that was 513
bytes. Read anything you intend to report *before* the transfer.

### 7.3 zsh does not word-split unquoted variables

`set -- $cfg` in a shell loop silently produced one argument instead of four, and every
benchmark row in that loop came back empty. Not a project bug, but it burned a cycle.

## 8. What I could not establish

* **Whether `attack_dir`'s geometry means what its name suggests** (§1.3). The step-20 bias
  makes the equal-angle case a flank; I report the raw angles and refuse to label them.
* **Any wasm-versus-native ratio** (§5.3). The two benchmarks do not measure the same
  simulation state and I will not manufacture a comparison out of them.
* **WebGL2 GPU time**, for the same reason as last round: no timestamp queries, and
  `gl.finish()` is not a fence in Chrome.
* **Whether the acquisition scan can be made cheap without changing behaviour.** I measured
  that it dominates (§5.3); I did not fix it, because a faster acquisition that picks a
  different target is a different simulation and this lane does not own that decision.
* **Anything above 4,096 worlds on the `sab` path.** 16,384 worlds × 64 units is in the
  draw-only data at 379 fps, but it was never swept with the simulation on workers.
* **Behaviour on any machine but this one.** One GPU, one browser, one OS. `bench.mjs`
  exists so re-measurement is one command.

## 9. Findings other lanes may care about

1. **`GroupCommand` can name at most 255 objects** (`num` is `unsigned char`), and its list
   entry is a **2-byte object index** (`GroupCommand::<unnamed-type-list> = struct { short
   o; }`, sizeof 2, from `rise.pdb`). How the engine selects a larger army is not derived.
   Anyone designing the RL action space needs both facts. [measured]
2. **`schema/command-wire.json` should be consumed by code generation, never transcribed**,
   and field widths are recoverable from consecutive offsets plus the wire size because the
   structs are packed. `web/tools/gen-wire.mjs` emits a JS codec and a Rust codec from it,
   and the 49 opcodes it shares with `crates/don-env`'s independently generated table agree
   on every wire size (§4.4). `don-net` could consume the same source instead of a
   hand-written table.
3. **Target acquisition, not the damage chain, is what makes a real tick expensive** —
   quadratic in world density, 30× throughput loss from 128 to 4,096 units in one world
   (§5.3). Any lane planning RL throughput should budget for acquisition, and any lane
   deriving the engine's real acquisition should know it is on the critical path.
4. **The live `Constants` block is directly usable as `don_sim::CombatRules`.** The 16
   values at `+0x44…+0xB98` map field-for-field onto that struct's declared order; the
   packer does it in twenty lines. Nobody needs to re-derive them from `rules.xml`.
5. **A shipped `UnitType` row is enough to fight with.** 190 of the 364 live rows are land
   units that can attack and move; deduplicated by display name they make a roster spanning
   ages 0–7, and the balance table gives every matchup between them. That is a ready-made
   scenario generator for the RL lane, and it is 500 KB.
6. **Cross-target determinism now covers real mechanics**, not just an integrator: identical
   digest, kills, damage and survivor count between aarch64 and wasm32 after 600 frames
   (§6). Cheap to run on every change:
   `cd web/wasm && cargo run --release --bin digest -- digest 4 2 64 128 600 0xC0FFEE`.
7. **The engine's Normal tick is 67 ms and the UI now says so.** `don_sim::TICK_HZ` is still
   15 from the `rules.xml` header; the difference is 0.5% but it is exactly the kind of
   constant that gets multiplied by a million frames in a throughput claim. The shim exports
   `sim_tick_ms()` = 67 and every "× real time" figure here uses 14.93 Hz.
8. **`Batch`-style per-world allocation is still the cluster path's structural cost**, as
   last round found. Unchanged and unaddressed; `web/wasm/src/real.rs` reproduces the same
   shape deliberately so the finding stays comparable.
