## 1. The correction: there are two `ICrossPlayService` declarations

This is the headline result and it inverts a starting assumption.

`CrossplayProxy.pdb` declares **both** of these, `size=4`, both with a vtable:

| declaration | virtual method records | actual vtable pointers | offsets |
|---|---|---|---|
| `CrossplayProxy::ICrossPlayService` | 58 | **58** | `0x000..=0x0e4` |
| `Crossplay::ICrossPlayService` | 97 | 96 | `0x000..=0x17c` |

(The 97-vs-96 gap is that slot 0 of the second one carries two method records,
`~ICrossPlayService` and `__vecDelDtor`, which occupy one pointer.)

**The 58-slot one is the shipped vtable.** Three independent measurements:

1. **Inheritance.** `CrossplayProxy::CrossPlayService` (size 2520) derives from
   `CrossplayProxy::ICrossPlayService` at offset 0 and overrides 58 of its
   slots, adding its own virtual destructor at `+0xe8`. **[measured]**
2. **Cross-PDB agreement.** `rise.pdb` and `CrossplayNetLib.pdb` each declare
   `Crossplay::ICrossPlayService` as **58 virtuals / 65 declared / size 4**, and
   a slot-by-slot comparison of (offset, name, signature) against
   `CrossplayProxy::ICrossPlayService` gives **zero differences across all
   three**. The two source trees spell the namespace differently; the layout is
   the same object. **[measured]**
3. **The emitted table.** `??_7CrossPlayService@CrossplayProxy@@6B@` at `.rdata`
   RVA `0x9adc4` holds 59 code pointers. Each of the first 58 resolves to
   `CrossplayProxy::CrossPlayService::<the name declared for that exact slot>`;
   `+0xe8` is the class's scalar deleting destructor; `+0xec` is already an
   `.rdata` address (the next object's RTTI locator). **[measured]**

The 96-slot `Crossplay::ICrossPlayService` comes from a **newer vendor header
this build does not use**. Its layout starts destructor / `SetNew` / `SetDelete`
/ `Init` / `Shutdown`, so `Init` — slot 0 in the real table — is at slot 3.
Every slot disagrees. It also carries APIs RoN:EE never got: `P2PEnableTcp`,
`SetP2PPacketOrderedDelivery`, `SetP2PMaxPacketLifetimeMs`,
`SetP2PAllowedPorts`, and a `CreateTicket`/`CancelTicket`/`SetMatchFoundCallback`
matchmaking family. **[measured]**

Treating the 96-slot record as the interface would produce an ABI that compiles
and is wrong in every slot. `netcode-symbols.md` §3.2 flagged this in prose;
this lane reproduces it from the PDBs and pins it with compile-time assertions
in `crates/don-crossplay/src/abi.rs`.

### 1a. The exported name is not the internal name

The PDB procedure at RVA `0x130e0` is
`?Service@CrossplayProxy@@YAPAUICrossPlayService@1@XZ` —
`CrossplayProxy::Service()` returning `CrossplayProxy::ICrossPlayService*`, from
`crossplayproxy.cpp:190`. The export table publishes **that same address** under
the game's spelling, `?Service@Crossplay@@YAPAUICrossPlayService@1@XZ`. Ordinal
1 needs no alias: `Crossplay::Logging::Logger` at `0x12180`
(`crossplaylogger.cpp:36`) is already exported under its own decorated name.
A replacement DLL must export the *game's* spelling. **[measured]**

The other two exports are the data symbols `AmdPowerXpressRequestHighPerformance`
(ord 3) and `NvOptimusEnablement` (ord 4) — the standard hybrid-GPU hints, not
interface. **[measured]**

### 2a. `LobbyDTO` is 208 bytes, and so is `m_lobby`'s offset

```text
+0    _id                  wstring (24)
+24   _ownerUserId         wstring (24)
+48   _sessionReference    wstring (24)
+72   _maxMembers          int
+76   _availableSlots      int
+80   _botCount            int
+84   _attributeVersion    int
+88   _visibitily          Lobby::Visibility     (sic — the field is misspelled)
+92   _members             vector<LobbyMemberDTO> (12)
+104  _attributes          unordered_map<wstring, wstring> (32)
+136  _turnServer          TurnServerDTO (72)
= 208
```

`netcode-symbols.md` §3.4 places `Crossplay::Lobby::DTO::LobbyDTO m_lobby` at
`CrossplayNetLibSys+208`, and `crates/netsys-shim` constructs its `m_lobby`
block at concrete `+0xD0` = 208. Those are an *offset* and a *size* that happen
to share a value; the real cross-check is that `CrossplayNetLib.pdb` and
`rise.pdb` both declare `LobbyDTO` with byte-identical fields to
`CrossplayProxy.pdb`'s, which they do. `_attributes` is the map that carries the
Party network descriptor and the recovered `game_seed` key.

### 2b. ABI shapes worth writing down

* Every virtual is `__thiscall`: `this` in `ECX`, args pushed right-to-left,
  **callee** cleans. **[measured — see §2c]**
* `sizeof(std::function<...>) == 40` for all 191 specialisations defined in this
  PDB, with the target pointer at `+0x24`. `SetServiceErrorCallback`
  (`0x100145c0`) reads `[arg+0x24]` directly. Same object `netsys-shim` calls
  `MsvcFunction40`. **[measured]**
* `sizeof(std::basic_string<wchar_t>) == sizeof(std::basic_string<char>) == 24`;
  `sizeof(std::vector<T>) == 12`; `sizeof(unordered_map<wstring,wstring>) == 32`.
  **[measured]**
* Both by-value and by-const-ref `std::function` parameters occur in the same
  table — e.g. `CreateLobby` takes its two callbacks **by value** (40 bytes each
  on the stack) while `JoinLobby` takes its two **by reference**. Collapsing
  them would misalign the stack by 72 bytes. **[measured]**
* One method returns a class by value: `GetInvitationId() const` returns
  `wstring`, so it takes a hidden caller-allocated return pointer as its first
  stack argument — the shape `netsys-shim` already uses for
  `NetPlayer::get_id`. **[measured]** for the return type, **[inferred]** for
  the hidden-argument position, which is unobservable here because the method
  has no other arguments.

### 2c. The `ret imm16` check

The PDB says what the parameters are; the machine code says how many bytes the
callee pops. For each of the 58 shipped slots the generator disassembles the
implementation the `.rdata` table points at, collects its `ret imm16`, and
compares it against the argument byte count derived from the signature:

**54 agree, 0 disagree, 4 indeterminate.** The four are
`SetJoinLobbyCallback`, `SetLeaveLobbyCallback`, `SetUpdateLobbyCallback` and
`LobbyCancelPendingRequests`, whose bodies end in a tail jump so a linear sweep
finds no `ret` at all — not a disagreement, an absence.

This is what makes the by-value/by-reference distinction above a measurement
rather than a reading of the type names. **[measured]**

## 3. Which slots retail actually dispatches — an assessment, with evidence

The task said to *note, not resolve*, which methods are game-critical. Rather
than rank the 58 names by how important they sound, this is measured:
`crates/don-crossplay/gen/slot_usage.py` follows the service pointer through
real machine code and records the vtable offset of every indirect call it
reaches.

Seeds: all **75** `call dword ptr [0x00ac503c]` sites in `riseofnations.exe`
(the IAT entry for `Crossplay::Service()`), and all **25**
`mov rX, [rY+0xcc]` loads of `CrossplayNetLibSys::m_crossplay` in
`CrossplayNetLib.dll`. Window: 200 instructions; volatile registers are dropped
across any intervening call; the scan stops at an unconditional branch.

**Read this as a one-sided detector.** A slot that appears *is* dispatched by
retail — that is a measurement. A slot that does not appear is **not** shown to
be unused; the tracker gives up on a spilled pointer, a longer window, or a
tail-merged path. **31 of 58** slots have a tracked dispatch.

### 3.3 Eleven slots are inert **in this shipped build**

Independent of who calls them, these implementations do nothing:

| slot(s) | body | RVA |
|---|---|---|
| 1, 3, 6, 9, 10, 26, 46, 52 | `ret 4` — one instruction, **ICF-folded onto a single address** | `0x145b0` |

to omit slots: they still occupy their vtable entries and are still called.

### 3.5 The assessment

Combining measured dispatch, implementation size and the netlib's own use, the
subset a DoN-owned `CrossplayProxy.dll` would have to serve for a match to
happen is, as an **assessment with the above evidence, not a decision**:

* **Lifecycle:** `Init`(0), `StartSession`(4), `StopSession`(5),
  `GetSessionStatus`(7), `Tick`(57). `GetSessionStatus` is the single most
  widely dispatched slot in the exe (17 distinct functions) and `Tick` is pumped
  from `NetDaemon::process_all`.
* **Lobby CRUD and attributes:** `GetLobby`(12), `FindLobbies`(13),
  `CreateLobby`(14), `JoinLobby`(15), `LeaveLobby`(17), `UpdateLobby`(19), plus
  the three result callbacks `SetJoinLobbyCallback`(16),
  `SetLeaveLobbyCallback`(18), `SetUpdateLobbyCallback`(20) — the DTO those
  callbacks carry is how `LobbyDTO::_attributes`, and therefore the
  `game_seed` key, reaches the game.
* **Match start:** `StartGame`(22), `CancelGameStart`(23), reached from
  `SetupWin`.
* **P2P:** the six `Set*Callback`s (40–45), `P2PSendToAll`(49), `P2PSend`(50),
  `P2PCloseAll`(51). `CrossplayNetLibSys::init` installs all seven callbacks in
  one function; `P2PSendToAll` is where every turn packet leaves.
* **Identity:** `GetPlayerGuid`(56) — 19 distinct call sites across both images.

Ignorable-looking, on the same evidence: leaderboards (29, 30), stats (27, 28),
blocking (9, 10, 11 — two are no-ops and the third is a constant `false`), lobby
and clan chat (24, 25, 34–39), invitations (31–33). None of those is on a path
between two peers and a running match.

### 3.6 Four methods people expect here do not exist in this build

`Shutdown`, `SetLobbyAttribute`, `SetLobbyAttributes` and
`SetLobbyMaxMemberCount` are **not in the shipped 58-slot interface**. They
exist only in the unshipped 96-slot vendor declaration, and a symbol sweep of
`CrossplayProxy.dll` finds **no implementation of any of them** — zero functions
whose name contains `SetLobbyAttribute` or `SetLobbyMaxMemberCount`.
**[measured]**

In this build, lobby attributes are set through the attribute map that
`CreateLobby(int maxMembers, Visibility, const unordered_map<wstring,wstring>&,
onOk, onErr)` and `UpdateLobby(const wstring& lobbyId, int, const
unordered_map<wstring,wstring>&, int, int, onOk, onErr)` take as a parameter,
and the max-member count is `CreateLobby`'s first `int`. Anyone planning around
a separate attribute setter is planning against the vendor SDK, not the game.

### 3.7 The overload hazard is real, but not where it was expected

The shipped 58-slot table has **no duplicate method names at all** — 58 distinct
names on 58 distinct slots. The `CreateLobby` ×2, `LeaveLobby` ×2, `JoinChat`
×2, `P2PSendToAll` ×2, `P2PSend` ×2 and `P2PClose` ×2 pairs are all in the
**vendor** table (slots 28/29, 32/33, 54/55, 70/71, 72/73, 75/76). **[measured]**

The one genuine overload in a *shipped* table is
`Crossplay::P2P::ICrossplayPlayer`, which has `Send(unsigned char*, int) const`
at slot 1 and `Send(const wstring&) const` at slot 2. The generator names them
`Send__s1` and `Send__s2` — it disambiguates by slot index, never by name, so
two same-named methods can never silently collapse onto one field.

**This is an assessment, not a measurement of necessity.** Nothing here observed
a running game; the only way to settle it is a load-only run of a replacement
that logs first use per slot, which is exactly what `netsys-shim`'s
`DON_NET_LOAD_ONLY=1` mode did for `NetSys` — and that requires separate
authorisation.

## 4. Licensing decision on the extracted JSON

The task asked whether the `pdb-extract` output for `CrossplayProxy.pdb` should
be committed to `schema/` as `schema/types.json` / `schema/symbols.json` are for
`rise.pdb`.

**Decision: no. Not committed.** Only the generator and the small generated
`abi.rs` are in the tree.

Reasoning:

* The two artifacts are 4.6 MB and 3.8 MB and constitute a **near-complete
  transcription of a proprietary private PDB** — every function name, its
  original source file path and line span, the full type catalogue, and the
  vendor's build-agent directory layout. README-LLM's licensing section is
  explicit that Microsoft/Big Huge Games PDBs and derived content are not
  covered by DoN's license and must not be committed or redistributed, and that
  a stable schema artifact is committed only when its provenance *and
  reproducibility* justify it.
* The existing `schema/{types,symbols}.json` for `rise.pdb` are a precedent, but
  precedent is not a licence to widen the exposure. They are pre-existing; this
  lane declines to add two more, and flags them as worth a deliberate review
  rather than quietly matching them.
* `schema/CrossplayProxy-symbols.tsv` (4,793 lines: address, section, decorated
  name) is already tracked, so the *symbol* surface for this DLL is not new
  exposure. The type catalogue, source paths and line numbers would be.
* Nothing is lost. `crates/don-crossplay/src/abi.rs` carries the exact facts
  this project needs, and `gen/gen_abi.py` reproduces the extraction in one
  command on any machine with a legally owned install. The generator records the
  PDB GUID and both SHA-256s in the emitted header, so a future reader can tell
  whether their inputs match the ones this file came from.

The same reasoning applies to the slot-usage table in §3: reproducible on demand
via `gen/slot_usage.py --json`, not committed.

## 5. Open, in priority order

1. **Nobody has observed a live call.** Every slot claim here is static. A
   load-only replacement that logs first use per slot would settle §3 exactly;
   `netsys-shim`'s `DON_NET_LOAD_ONLY=1` is the working precedent, and it needs
   separate authorisation.
2. **PlayFab authentication and the title id** remain the real blocker for any
   independent path, exactly as `netcode-symbols.md` §5 Option B said. Not
   touched by this lane.
3. **The lobby attribute key schema.** `CrossplayProxy::QlocLobbyPropertyData`
   has static consts `PLAYFAB_SEARCH_KEY_PREFIX`, `SEARCH_DATA_VALUE_SEPARATOR`,
   `SEARCH_DATA_PAIR_SEPARATOR` and a `QLOC_PROPERTY_KEYS_MAP`, and
   `QlocLobbyMemberData` has `USERNAME_KEY`, `PLATFORM_KEY`, `PLATFORM_ID_KEY`,
   `VERSION_ID_KEY`, `ATTRIBUTE_PREFIX`. Their *values* live in `.rdata` and
   were not read here. That is the schema for publishing a joinable session.
   **[measured that the symbols exist; values unestablished]**
4. **`CrossPlayService`'s 2520-byte object layout** was not transcribed. Only
   `+0x930` (session status) is recorded, from the two one-line accessors.
5. **`JoinLobbyResultDTO`** (216 bytes) is declared in `rise.pdb` but not in
   `CrossplayProxy.pdb`. Either the game reads it from somewhere else or it is
   dead in this build; unresolved.
